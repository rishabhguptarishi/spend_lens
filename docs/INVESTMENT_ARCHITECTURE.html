Investment & Statement Architecture

SpendLens, the unification plan. How to make the app a true single source of truth for bank statements, investments, and tax docs — without the parser breaking on every new bank, and without the same money being counted twice across sources.

Status Draft v1.1 Date 2026-05-26 Owner Rishabh Scope Phase 0 shipped; Phase 1 next

Decisions log — resolved since v1

  • CSV-first UX: ✓ confirmed. CSV/XLSX becomes the recommended upload path; PDF falls back.
  • Tier-2 bank rollout order: ✓ confirmed. Kotak → IDFC First → Yes → Federal → BoB → IndusInd → PNB → Canara, one parser per PR.
  • Low-confidence parses: ✓ confirmed. AI extractor (with per-field confidence) is the fallback; manual line entry is the last resort.
  • MFCentral integration: ✗ not possible — SEBI/AMFI shut down MFCentral in September 2025.   • Additional asset classes: ✓ 5 added — reit, invit, p2p, fractional_re, rsu — see §3.2.8 and §5.2 for identity-key conventions.

1 · Context — why this document exists

The product has grown into a super-app that overlaps three categories:

  1. A bank-statement aggregator (HDFC, ICICI, Axis, SBI, …)
  2. An investment portfolio tracker (stocks, MFs, FDs, PPF, NPS, …)
  3. A tax-filing assistant (ITR forms, deduction tracking, capital gains)

These three are tightly coupled — investments live inside bank statements, tax docs reflect investment activity, and the user’s mental model is one wallet, not three apps. But the codebase has grown organically, each new feature adding its own ingestion path with its own dedup logic, and the parser has been tuned to specific samples (Axis salary, ICICI consolidated, HDFC savings). Every new statement format breaks something.

Two specific complaints driving this rewrite:

“We’re only considering Zerodha.” Reality: Groww is #1 (1.3Cr active users), Zerodha is #2 (68L), Angel One is #3 (67L), then ICICI Direct, Upstox, HDFC Securities, Kotak Securities, SBI Securities, Dhan, Motilal Oswal. And that’s just brokers — add MF aggregators (Kuvera, ET Money, Coin), industry platforms (MFCentral, MFU), retirement (NPS, EPF), insurance, RBI Retail Direct, crypto. We need to support all of them, not optimise for one.

“The parser keeps breaking on new bank statements.” Reality: there are 12 large private banks, 12 PSU banks, 11 small finance banks, 6 payments banks in India — each with its own PDF layout. We need a parser strategy that survives format drift.

This doc consolidates: (a) the audit of where we are, (b) the catalog of institutions we need to support, (c) the parser strategy that won’t break, (d) the architecture that fixes the double-counting, and (e) a phased roadmap.

2 · Audit summary — current state

The headline numbers from a thorough audit of app/services, app/models, app/controllers:

  • 14 different writers create investment rows, each with its own dedup logic
  • 17 specific architectural gaps (half-built columns, unused fields, case-sensitive account names, etc.)
  • 8 active double-counting paths in production (see below)
  • 1 place where dedup works cleanly: StatementParsing::PortfolioExtractor for ICICI PPF/FD/RD (folio-keyed)
  • 0 places where ISIN or symbol is used as a holding identity key, despite every parser populating those fields

The 8 active double-counting paths

  1. PPF balance + bank-detect contribution → inflated PPF
  2. FD interest accrual + bank-detect interest credit → double interest
  3. Form 16A FD interest + bank-detect interest + passbook accrual → triple counted
  4. Broker P&L doc + broker CSV → realized gain doubled (account names differ)
  5. MF CAS SIPs + bank-detect AMC SIPs → contribution doubled (different accounts)
  6. CDSL CAS holding + broker CSV → equity doubled (cost basis + market value)
  7. CDSL CAS MF folio + MF CAS folio → MF doubled across registrars
  8. Capital Gains UI: investment_transactions sells AND document_stcg both shown without subtraction

TypeListed examplesIdentity keyStatus

Why these need their own asset class — they trade like stocks (have ISINs, settle in demat) but their quarterly/half-yearly distributions split into three tax buckets:

Distribution componentTax treatmentActivity sub-kind
DividendTaxable at slabdividend
InterestTaxable at slabinterest
Capital repayment / return of capitalReduces cost basis — not incomecapital_return (reduces position cost basis on calculation)

If we treated these as ordinary stocks, the capital-gains calc on sale would be wrong (cost basis would be inflated; user pays excess LTCG). Distinct asset class lets the parser tag each component correctly and the CG service apply the right tax rule.

LendingKart, Faircent, IndiaP2P, LiquidLoans, 12% Club, Mobikwik Xtra (P2P), Cred MintPlatform monthly statement + annual interest certificateP2P:<platform>:<investor_id>✗ new asset_class

4 · Parser robustness strategy

The goal: when a user uploads a statement from a bank we’ve never seen, we should still extract the right transactions and degrade gracefully — not crash, not produce wrong numbers, not silently miss rows.

4.1 Input-format priority pipeline

┌─── Tier 1: STRUCTURED ──────────────────────────────────────────┐ │ CSV / XLSX → deterministic column mapper, ~99% accuracy │ │ OFX / QFX / MT940 → ISO 20022 parser │ │ HTML email → table extractor │ └─────────────────────────────────────────────────────────────────┘ ↓ (fallback) ┌─── Tier 2: DIGITAL PDF (text layer) ────────────────────────────┐ │ A. Detect bank via fingerprint (IFSC prefix, header URL) │ │ B. Bank-specific regex parser (the §3.1 Tier-1 banks) │ │ C. Fallback to generic table-extractor (pdfplumber-style) │ │ D. Fallback to AI extraction (Ollama via AiClient) │ │ E. Hash-based dedup across re-uploads │ └─────────────────────────────────────────────────────────────────┘ ↓ ┌─── Tier 3: SCANNED PDF / IMAGE ─────────────────────────────────┐ │ OCR (Tesseract) → text → re-enter Tier 2 │ └─────────────────────────────────────────────────────────────────┘ ↓ ┌─── Tier 4: VISION LLM ──────────────────────────────────────────┐ │ Multimodal model (when text layer absent or garbled) │ └─────────────────────────────────────────────────────────────────┘

Every transaction emitted carries:

  • extraction_method ∈ [deterministic, table, ai_text, ocr, vision_llm]
  • confidence ∈ [0, 1]
  • parser_version (per-bank parser version)

Low-confidence rows go to a review queue in the UI — never silently swallowed, never silently published.

4.2 Bank-fingerprint registry

Replace today’s scattered axis_statement? / icici_statement? boolean methods with a registry:

# config/initializers/bank_fingerprints.rb (illustrative)
BankFingerprintRegistry.register('HDFC Bank',
  ifsc_prefix: 'HDFC0',
  header_patterns: [/HDFC\s+BANK/i, /hdfcbank\.com/i],
  parser: StatementParsing::Banks::HdfcParser,
  sample_path: 'spec/fixtures/statements/hdfc_savings_sample.pdf')

BankFingerprintRegistry.register('ICICI Bank',
  ifsc_prefix: 'ICIC0',
  header_patterns: [/ICICI\s+Bank/i, /icicibank\.com/i, /Cust\s+ID/i],
  parser: StatementParsing::Banks::IciciParser,
  features: %i[multi_account_sections portfolio_extraction],
  sample_path: 'spec/fixtures/statements/icici_consolidated_sample.pdf')

# ... 12 Tier-1 banks ...

When a new bank statement uploads:

  1. Look up by ifsc_prefix from the metadata extractor
  2. If no match, try header_patterns regex
  3. If still no match → log “unsupported bank”, route to AI extractor, flag for parser_coverage metrics

4.3 Per-bank regression suite

For every bank we claim to support, the spec suite must contain:

  • 1 golden sample PDF in spec/fixtures/statements/<bank>_<account_type>_sample.pdf
  • Golden expected transactions in spec/fixtures/statements/<bank>_<account_type>_expected.yml
  • Spec verifies parsing matches expected exactly (within ₹0.01)
  • Balance verification: opening + Σcredits − Σdebits = closing must pass

When a user reports “parser broke for X”, first action: add their sanitized statement to the regression suite, then fix.

4.4 Versioned parsers

Banks change their PDF layout 1–2× per year. The parser registry tracks version:

class StatementParsing::Banks::IciciParser
  VERSION = '2026.05'  # last verified working
  CHANGELOG = [
    '2026.05: Added multi-account section parsing (PPF + Savings + FD)',
    '2026.03: Initial implementation',
  ]
end

If a future statement breaks, parser falls through to AI extractor and logs a “drift detected” event. Engineering can then bump the parser version + add new golden sample.

4.5 Balance verification (the golden rule)

Every statement parser must emit an opening_balance and closing_balance from header/footer text. The system then verifies:

opening_balance + Σ(credit amounts) − Σ(debit amounts) ≈ closing_balance ± ₹0.50

If it doesn’t match, the statement is flagged as parse_quality: 'unreliable' and the user sees a warning banner. This catches ~90% of parse drift.

4.6 CSV-first encouragement

Most major Indian banks let you download CSV/XLSX from net banking:

BankPath

SBIYONO/Net Banking → Accounts → Account Statement → Download CSV/Excel

5 · Proposed architecture

5.1 Three-layer data model

LAYER 1 — INSTRUMENTS (canonical, one row per real-world security/account) ├── id, user_id, asset_class, identity_key, label, currency, metadata └── UNIQUE INDEX (user_id, identity_key) WHERE identity_key IS NOT NULL LAYER 2 — POSITIONS (computed from activities; refreshed on demand) ├── id, user_id, instrument_id, custodian_id, units, cost_basis, │ current_value, as_of_date └── UNIQUE INDEX (user_id, instrument_id, custodian_id) LAYER 3 — ACTIVITIES (immutable transaction log, one row per real-world event) ├── id, user_id, instrument_id, custodian_id, date, kind, units, amount, │ description, source, source_priority, external_id, confirmed_by, │ superseded_by_id, transaction_id (← bank txn link) └── UNIQUE INDEX (user_id, external_id) WHERE external_id IS NOT NULL

Replaces today’s confused use of InvestmentHolding (mixed: cost basis + balance), InvestmentTransaction (no external_id), and InvestmentAccount (mixed: custodian + source label).

When a higher-priority source arrives that matches a lower-priority activity (same instrument, ±1 day, ±2% amount), the system:

  1. Adds the higher-priority source name to confirmed_by on the lower-priority activity
  2. Marks the lower-priority activity as superseded_by_id: <higher> (kept for audit, hidden from totals)

5.6 What happens for each ingestion pathway (concrete examples)

Example A — ICICI consolidated statement

  1. StatementParserService parses bank txns (savings-only, as today).
  2. PortfolioExtractor extracts PPF balance, FD list, RD list:
    • Each FD → Instrument(identity_key: 'FD:icici:153913018495', asset_class: 'fd')
    • Position (user, instrument, custodian: 'ICICI Bank') with cost basis from dep_amt
    • Activity (kind: 'buy', date: open_date, source: 'bank_statement_passbook', external_id: 'passbook:icici:153913018495:2026-02-07')
    • Same statement re-uploaded → external_id collides → no duplicate.
  3. Bank-detect scans savings txns:
    • Trf to PPF 000418336506 → suggestion with instrument_hint: 'PPF:icici:000418336506'
    • On accept: activity with external_id: 'bank_txn:<id>', priority 60
    • Reconciler sees existing passbook activity for same PPF (priority 75) → supersedes → no double-count.

Example B — Zerodha CSV + their bank statement separately

  1. Zerodha CSV → activities with external_id: 'zerodha:order:<id>', priority 80, custodian Zerodha.
  2. Bank statement → savings txns including UPI-ZERODHA… debits → bank-detect suggestions.
  3. On accept → activities with external_id: 'bank_txn:<id>', priority 60.
  4. Reconciler matches by date + amount + custodian → tags Zerodha CSV as confirmed by bank-detect.
  5. UI shows one row per instrument, with ✓ matched across 2 sources badge.

Example C — CAMS CAS for HDFC Top 100 MF + bank statement with HDFC AMC SIPs

  1. CAMS CAS → activity per SIP, external_id: 'cams:11223344/HDFC:2026-04-05:25.43:8023.45', priority 95.
  2. Bank-detect sees HDFC MF SIP debits → suggestions → accepted → priority 60.
  3. Reconciler matches by date + amount + AMC name → bank-txn activities marked as superseded.
  4. Folio number now extracted into instrument metadata.

Example D — broker P&L tax doc + already imported Zerodha CSV

  1. Broker CSV gave activities at priority 80.
  2. Tax-doc sync gives activities at priority 90, custodian “Zerodha” (NOT “Broker (tax P&L)” anymore).
  3. Reconciler matches by symbol + date + amount → broker CSV activities marked as confirmed_by the tax doc.
  4. Capital Gains UI uses priority-90 activities (audit-grade) → STCG/LTCG no longer doubled.

  • IFSC — Indian Financial System Code (bank branch identifier, also identifies bank)
  • DP — Depository Participant (broker, as seen by CDSL/NSDL)
  • AIS / TIS / 26AS — Income Tax department’s view of your finances
  • SOA — Statement of Account (non-demat MF holding form)
